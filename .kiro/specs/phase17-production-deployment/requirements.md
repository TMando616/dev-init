# Phase 17: 本番環境への初回デプロイ（無料枠内）

## 概要

**目的**: DevInitを実際にインターネット上で動かし、無料の範囲でフロントエンド・バックエンド・DB・コード実行サンドボックスを含めて運用できる状態にする。

**対象ユーザー**: プロジェクトオーナー（運用者）自身。エンドユーザー（学習者・管理者）はデプロイ後にこのアプリへアクセスする。

**背景・制約**:
- コード実行機能（`CodeExecutionService`）はバックエンドコンテナの中から `docker run` を直接実行し、PHP/Python/JavaScript/Ruby/Java を隔離コンテナで動かす設計（`--network none`, 128MB, 5秒タイムアウト）。これはホストのDockerデーモンへのアクセスを要求するため、一般的なPaaSの無料枠（Render / Railway / Fly.ioの共有CPUプラン等）では動かせない。
- 上記の制約により、**単一の無料VM上でフロント・バック・DB・コード実行を全て同居させる方針**を採用する（Oracle Cloud Infrastructure Always Free の ARM Ampere A1インスタンスを想定）。
- 使用中のDockerイメージ（`php:8.4-fpm-alpine`, `php:8.4-cli-alpine`, `python:3.12-alpine`, `node:22-alpine`, `ruby:3.3-alpine`, `amazoncorretto:21-alpine`, `postgres:16-alpine`, `nginx:alpine`, `axllent/mailpit`, `node:20-slim`, `composer:latest`）はarm64マニフェストを持つことを確認済み（`node:20-slim`・`composer:latest`はDocker Hubのレート制限で直接未確認だが、広く使われる公式マルチアーキイメージのため互換性リスクは低いと判断）。
- 現在の `docker-compose.yml` は開発用構成（`next dev`、Mailpit、ポート80への直接バインド等）であり、そのままでは本番運用に適さない。

**今回の方針決定（確定事項）**:
- インフラは Oracle Cloud Infrastructure（OCI）の Always Free 枠（ARM Ampere A1, 4 OCPU / 24GB RAM, 永年無料）を使う。
- フロント・バック・DB・コード実行は同一VM上で `docker compose` により稼働させる（現行のローカル開発構成を本番向けにオーバーレイする形。マネージドPaaSへの分散は行わない）。
- HTTPS化は Let's Encrypt の無料証明書を使う（Caddy等、自動更新できるリバースプロキシを想定）。
- 独自ドメインは取得せず、VMのグローバルIPに対して `sslip.io`（無料IPベースホスト名サービス）を使う。実際に解決可能なホスト名として扱えるため、Let's Encrypt証明書を発行できる（例: `https://<VMのIP区切り>.sslip.io`）。将来的に独自ドメインへ切り替えることも可能。
- メール送信（パスワードリセット等）は開発用のMailpitではなく、Resend（無料枠: 3,000通/月・100通/日）のSMTP認証情報に差し替える。自前ドメインがなくてもResend提供の送信元アドレスで開始できる。
- DBは同一VM上のPostgreSQLコンテナをそのまま使う。外部マネージドDBサービスへの移行は本フェーズでは行わない。
- CI/CDによる自動デプロイ、監視・アラート基盤の整備、ステージング環境の用意は**本フェーズの対象外**とする（必要になれば別フェーズで扱う）。

## ユーザーストーリー

### US-1: 本番環境での起動

**As a** 運用者
**I want** フロントエンド・バックエンド・DB・コード実行サンドボックスを1つのVM上で無料のまま稼働させたい
**So that** コストをかけずに実際のユーザーにサービスを提供できる

#### 受け入れ条件

- [ ] OCI Always Free の ARM Ampere A1 インスタンスがプロビジョニングされている
- [ ] VM上で `docker compose`（本番用オーバーレイ）により全サービスが起動する
- [ ] フロントエンドは開発用の `next dev` ではなく、本番ビルド（`next build` → `next start`、または同等の最適化された起動方法）で動作する
- [ ] コード実行（PHP/Python/JavaScript/Ruby/Java）がVM上で実際に成功する（`docker run` がARM上で問題なく動く）
- [ ] VMを再起動してもサービスが自動的に立ち上がる（`restart: always` あるいは systemd 等での担保）

---

### US-2: HTTPSでのアクセス

**As a** エンドユーザー
**I want** サービスにHTTPS経由でアクセスしたい
**So that** 通信内容（ログイン情報等）が保護される

#### 受け入れ条件

- [ ] `http://` へのアクセスは `https://` にリダイレクトされる
- [ ] TLS証明書はLet's Encrypt等の無料証明書で、自動更新される仕組みになっている
- [ ] `sslip.io` のIPベースホスト名でアクセスでき、ブラウザで証明書エラーが出ない

---

### US-3: 本番用シークレット・環境変数の管理

**As a** 運用者
**I want** 本番用の機密情報（`APP_KEY`, DBパスワード, SMTP認証情報等）をリポジトリに含めず安全に管理したい
**So that** 秘密情報の漏洩を防ぐ

#### 受け入れ条件

- [ ] 本番用 `.env` はGit管理下に置かず、VM上にのみ配置される
- [ ] `APP_ENV=production`, `APP_DEBUG=false` になっている
- [ ] `APP_KEY` は本番用に新規生成されている（開発用と共用しない）
- [ ] DBのユーザー名・パスワードは開発用のデフォルト値（`user`/`password`）から変更されている
- [ ] `FRONTEND_URL` / `APP_URL` が本番の `sslip.io` ホスト名を指している
- [ ] `MAIL_*` がResendのSMTP認証情報になっている

---

### US-4: データの永続化とバックアップ

**As a** 運用者
**I want** VMを再起動してもデータが失われず、最低限のバックアップ手段を持ちたい
**So that** 障害時にサービスとデータを復旧できる

#### 受け入れ条件

- [ ] PostgreSQLのデータがDockerボリュームとしてVMのディスク上に永続化されている
- [ ] `docker compose down` / VM再起動後もデータが失われない
- [ ] 最低限のバックアップ手段（例: 日次の `pg_dump` をVM上または無料の外部ストレージに保存するcronジョブ）がある
- [ ] リストア手順が確認されている（バックアップから実際に復元できることを一度は検証する）

---

### US-5: 初回セットアップの運用性

**As a** 運用者
**I want** 初回デプロイの手順と、その後の更新（`git pull` して再デプロイ）の手順が明確になっている状態にしたい
**So that** 次回以降の変更を迷わず本番へ反映できる

#### 受け入れ条件

- [ ] 初期管理者アカウントを本番DBに作成する手順が確立している（開発用シーダーをそのまま使わない場合はその代替手順が明確）
- [ ] `main` ブランチの変更をVM上に反映する手順（`git pull` → イメージ再ビルド → `docker compose up -d` 等）が文書化されている
- [ ] デプロイ後、ログ（`docker compose logs`）を確認する手順がある
- [ ] ヘルスチェック（各サービスが正常に応答しているかの簡易確認方法）がある

---

## ギャップ分析（既存実装との差分）

### インフラ・Docker構成

| 対象 | 現状 | 本フェーズでの変更 |
|------|------|------------------|
| `docker-compose.yml` | 開発専用（ポート80直接バインド、Mailpit、DB接続情報がハードコード気味） | 本番用オーバーレイ（`docker-compose.prod.yml` 等）を新設し、リバースプロキシ・TLS・restart policyを追加 |
| `docker/node/Dockerfile` | `CMD ["npx", "next", "dev"]`（開発サーバー） | 本番ビルド用のマルチステージDockerfileに変更（`next build` → `next start`） |
| nginx | HTTPのみ、開発用ルーティング | Caddy等に置き換える、またはnginxにTLS終端を追加（Let's Encrypt自動更新の実現方法を設計で確定） |
| `.env` (backend) | 開発用デフォルト値がリポジトリの `.env.example` に記載 | 本番用の値をVM上にのみ作成。`MAIL_*` を実SMTPに差し替え |
| DB | 開発用の固定ユーザー名/パスワード | 本番用の強固な認証情報に変更 |
| バックアップ | なし | `pg_dump` の定期実行の仕組みを追加 |

### インフラ以外

- アプリケーションコード（バックエンド・フロントエンド）自体の変更は基本的に不要（ARM互換性は確認済み）。ただし `next dev` → `next start` への切り替えに伴い、ビルド時の環境変数埋め込み（`NEXT_PUBLIC_API_URL`）の扱いを設計で確認する必要がある。

## 個人情報の取り扱いに関する注記

本番環境で実際の受講生・管理者の個人情報（氏名・メールアドレス・学習履歴）を扱うことになるため、以下を確認する。

| 項目 | 状況 | 対応要否 |
|------|------|------|
| プライバシーポリシー | 未整備 | 実在ユーザーが登録する前に用意を検討（本フェーズのスコープ外だが、公開前に要判断） |
| 同意取得 | 受講生登録フォームに同意チェックボックスなし | 同上 |
| バックアップデータの保管場所 | 未定 | 個人情報を含むバックアップの保存先・保持期間を設計で決める |
| SMTP送信先の第三者提供 | Resendにメールアドレスが渡る | Resendのプライバシーポリシー・データ保持方針を確認する |

## 対象外（Out of Scope）

- CI/CDによる自動デプロイ
- 監視・アラート基盤（Datadog等の導入）
- ステージング環境
- 水平スケーリング・複数VM構成
- マネージドDB（RDS等）への移行
- CDN導入
- プライバシーポリシーページの作成（別途判断）

# Phase 16: 管理者アカウント機能の整備

## 概要

**目的**: 管理者が自分のアカウント情報を自分で管理できるようにする。Phase 15 で受講生に用意したプロフィール編集・パスワード変更・パスワードリセットの3導線を、`admins` 側にも揃える。

**対象ユーザー**: 管理者。受講生側の挙動は一切変えない。

**背景・課題**:
- Phase 15 で受講生は自分で名前・メールアドレス・パスワードを変更できるようになったが、**管理者は登録時の情報を一切変更できない**（`AdminAuthController` は `login` / `logout` / `me` のみ）。誰かに作ってもらったアカウントの初期パスワードを使い続けるしかない。
- 管理者にパスワードリセットの導線がない。管理者はブラウザ上で自力復旧できず、**パスワードを忘れると他の管理者に消してもらって作り直すしかない**。管理者が1人しかいない状態でこれが起きると、DBを直接触る以外に復旧手段がなくなる。
- `Admin` モデルは `Notifiable` を持つが `sendPasswordResetNotification()` を持たず、`config/auth.php` の `passwords` に `admins` ブローカーの定義もない。Phase 15 で整備したメール基盤（Mailpit・`FRONTEND_URL`・日本語通知）はそのまま流用できる。
- 管理画面に「自分の情報」を扱う画面が存在しない。`/admin/admins`（管理者管理）は他人を招待・削除する画面で、自分自身の編集導線はない。

**今回の方針決定（確定事項）**:
- 受講生側の実装（`AccountController` / `AccountService` / `PasswordResetService` / 各 FormRequest）を**そのまま流用せず、管理者用に分けて実装する**。ガードが `sanctum`（`users`）と `admin`（`admins`）で異なり、`current_password:sanctum` やトークン失効の対象も別物のため。ただし設計の形（Controller → Service → Repository、FormRequest でのバリデーション、`throttle:account` 相当のレート制限）は Phase 15 に揃える。
- パスワードリセットは**本フェーズに含める**。`config/auth.php` に `admins` ブローカーを追加し、専用のトークンテーブルを新設する。理由は Phase 15 と同じで、Laravel 標準の `password_reset_tokens` は email だけをキーにするため、受講生と管理者が同じメールアドレスを持てる現状では**リセットリンクが取り違えられる**。
- 管理者の**退会（自己削除）は対象外**とする。管理者アカウントは他の管理者が招待して作り、不要になったら他の管理者が削除する運用（`DELETE /api/admin/admins/{id}`、自己削除は禁止済み）を維持する。この運用のおかげで「最後の1人が自分を消してログインできる管理者がいなくなる」事態が構造的に起きない。
- 管理者に**ソフトデリート・復会は導入しない**。受講生の退会にソフトデリートを入れたのは学習進捗を引き継ぐためで、管理者にその要件はない。現在の物理削除のままとする。
- 管理者の **MFA・RBAC（権限レベルの分離）は対象外**（phase6 の design.md §7 に将来課題として記録済み。本フェーズでも引き続き対象外とする）。
- 管理者トークンの httpOnly Cookie 化も**対象外**（同じく phase6 §7 の将来課題）。

## ユーザーストーリー

### US-1: 管理者のプロフィール（名前・メールアドレス）の編集

**As a** 管理者
**I want** 自分の名前とメールアドレスを管理画面から変更したい
**So that** 招待時に登録された情報や、変わった連絡先を自分で直せる

#### 受け入れ条件

- [ ] 管理者としてログインした状態で、管理サイドバーから設定画面（`/admin/settings`）へ遷移できる
- [ ] 設定画面に現在の名前・メールアドレスが初期値として表示される
- [ ] 名前を変更して保存すると、レスポンスと画面表示（サイドバーの管理者名を含む）に即座に反映される
- [ ] メールアドレスを変更して保存すると、変更後のメールアドレスでログインできる
- [ ] メールアドレスを変更する場合は**現在のパスワードの入力が必要**で、誤っていると422が返る（名前だけの変更には不要。US-1 の受講生側と同じ扱い）
- [ ] 他の管理者が既に使っているメールアドレスに変更しようとすると422が返り、画面にエラーメッセージが表示される
- [ ] 自分自身の現在のメールアドレスのまま保存した場合は、重複エラーにならず正常に保存できる
- [ ] **受講生（`users`）が使っているメールアドレスとの重複は許容する**（`admins` と `users` は別テーブルで、同一人物が両方のアカウントを持つ運用を妨げない）
- [ ] 未ログイン、または受講生トークンで管理者用の更新APIを叩くと401が返る
- [ ] バリデーションはFormRequestに定義する（Controller内での `validate()` 直書きをしない）

---

### US-2: 管理者のパスワード変更

**As a** 管理者
**I want** ログイン中に自分のパスワードを変更したい
**So that** 招待時の初期パスワードを使い続けずに済み、漏洩が疑われるときも自分で対処できる

#### 受け入れ条件

- [ ] 設定画面に「現在のパスワード」「新しいパスワード」「新しいパスワード（確認）」の入力欄がある
- [ ] 現在のパスワードが誤っている場合は422が返り、パスワードは変更されない
- [ ] 新しいパスワードは8文字以上・確認入力との一致（`confirmed`）を満たさない場合422になる
- [ ] 変更に成功すると、新しいパスワードでログインでき、古いパスワードではログインできない
- [ ] 変更に成功すると、**操作中の端末以外のアクセストークンは全て失効する**（別端末は再ログインが必要になる）
- [ ] 変更後も操作中の端末はログアウトされず、そのまま操作を続けられる
- [ ] パスワード変更エンドポイントは `throttle:account` 相当の厳しめのレート制限下にある

---

### US-3: 管理者のパスワードリセット（メール経由）

**As a** パスワードを忘れた管理者
**I want** メールで届いたリンクからパスワードを再設定したい
**So that** 他の管理者やDB操作に頼らず自力で復旧できる

#### 受け入れ条件

- [ ] 管理者ログイン画面（`/admin/login`）に「パスワードをお忘れの方」リンクがあり、`/admin/forgot-password` へ遷移できる
- [ ] `/admin/forgot-password` でメールアドレスを送信すると、登録済み・未登録にかかわらず**同一の成功メッセージ**が表示される（アカウントの存在有無を推測されないため）
- [ ] 登録済みの管理者メールアドレスの場合、リセットリンクを含むメールが送信される
- [ ] メールの件名・本文から**管理者向けのリセットであることが分かる**（受講生向けメールと取り違えない）
- [ ] 開発環境では Mailpit（`http://localhost:8025`）でそのメールを確認できる
- [ ] メール内のリンクはフロントエンドの `/admin/reset-password?token=...&email=...` を指しており、クリックすると再設定フォームが開く
- [ ] 新しいパスワードを送信すると変更が完了し、そのパスワードで管理者ログインできる
- [ ] リセットに成功すると、その管理者の**既存アクセストークンは全て失効する**（Phase 15 の受講生側と同じ扱い）
- [ ] 一度使用したトークンは再利用できない（2回目は422）
- [ ] 有効期限切れ・改ざんされたトークンでは再設定できず、エラーメッセージが表示される
- [ ] **同じメールアドレスの受講生が存在しても、管理者のリセットリンクで受講生のパスワードが変わらない**（逆も同様）
- [ ] 受講生用の `/api/forgot-password` に管理者のメールアドレスを送っても、管理者宛にはメールが送られない
- [ ] `/admin/forgot-password`・`/admin/reset-password` の両APIは `throttle:auth` 相当のレート制限下にある

---

### US-4: 管理者削除時のあと片付け

**As a** サービス運営者
**I want** 管理者を削除したときに、その人に紐づく認証情報が残らないようにしたい
**So that** 削除後に古いトークンやリセットリンクが生き残らない

#### 受け入れ条件

- [ ] 管理者を削除すると、その管理者の全アクセストークンが失効する
- [ ] 管理者を削除すると、その管理者宛の未使用のパスワードリセットトークン行も削除される
- [ ] 削除された管理者のトークンで管理者APIを叩くと401が返る
- [ ] 自己削除が禁止されている既存の挙動は変わらない（400が返る）

## ギャップ分析（既存実装との差分）

### バックエンド

| 対象 | 現状 | 本フェーズでの変更 |
|------|------|------------------|
| `app/Models/Admin.php` | `Notifiable` はあるが `sendPasswordResetNotification()` なし | 管理者向け日本語通知を送るようオーバーライド（`User` と同じ形） |
| `config/auth.php` | `passwords` は `users` ブローカーのみ | `admins` ブローカーと専用トークンテーブルを追加 |
| リセットトークンのテーブル | `password_reset_tokens`（受講生と共用になってしまう） | 管理者用テーブルを新設。`users` と `admins` で同じメールアドレスが使える以上、共用は取り違えを生む |
| `app/Http/Controllers/AdminAuthController.php` | `login` / `logout` / `me` のみ | 変更しない（自分の情報の更新は新しい Controller に置き、責務を分ける。Phase 15 で `AuthController` を太らせなかったのと同じ方針） |
| アカウント操作の Controller / Service | 存在しない（`AdminService` は他人の招待・削除のみ） | 管理者版の `AccountController` / `AccountService` 相当を新設。配置とクラス名は設計で確定 |
| `app/Repositories/AdminRepository.php` | `all` / `find` / `findByEmail` / `create` / `delete` | 更新系のメソッドを追加（`update` が無い） |
| `app/Services/AdminService.php` | `delete` はトークン失効を行わない | 削除時に全トークン失効 + リセットトークン行の削除を追加（US-4）。Phase 15 の `UserService::delete` と同じ対応 |
| `routes/api.php` | 管理者の自己操作系ルートなし | `auth:admin` 配下にプロフィール更新・パスワード変更、公開側（`throttle:auth`）にリセット系2本を追加 |
| `app/Providers/AppServiceProvider.php` | `account` リミッターは `$request->user()?->id` でキーを引く | 管理者にも流用できるか確認（`auth:admin` でも `$request->user()` は解決されるため流用できる見込み。設計で確定） |
| FormRequest | 管理者関連は `AdminLoginRequest` / `Admin\StoreAdminRequest` のみ | プロフィール更新・パスワード変更・リセット系のリクエストを追加 |
| 通知 | `ResetPasswordNotification`（受講生向け文面） | 管理者向けの通知クラスを追加（文面とリンク先が異なるため流用しない） |

### フロントエンド

| 対象 | 現状 | 本フェーズでの変更 |
|------|------|------------------|
| 管理者ページ | `/admin`, `/admin/materials`, `/admin/categories`, `/admin/users`, `/admin/admins`, `/admin/login` | `/admin/settings`, `/admin/forgot-password`, `/admin/reset-password` を追加 |
| `components/AdminSidebar.tsx` | レッスン / 学習資料 / カテゴリ / 生徒 / 管理者管理の5項目 | 「設定」への導線を追加 |
| `context/AdminAuthContext.tsx` | `admin` / `login` / `logout` / `checkAuth` を提供 | プロフィール更新後の再取得（`refreshAdmin` 相当）を追加 |
| `lib/adminApi.ts` | 401時の除外パスが `/admin/login` のハードコード | 管理者側の公開パスが3つに増えるため、受講生側の `lib/routes.ts` と同じく一元化する（Phase 15 で踏んだ「リセットリンクを開くと `/login` に飛ばされる」不具合の再発防止） |
| ダークモード | 全画面対応済み | 新規3画面も `dark:` バリアントを最初から持たせる |

### テスト

- 管理者のプロフィール更新・パスワード変更は新規テストファイルを作成する
- 管理者のパスワードリセットは `Notification::fake()` で検証し、実メール送信に依存しない
- **同一メールアドレスの受講生と管理者が併存する状態**を作り、リセットが互いに干渉しないことを検証する（本フェーズ特有のリスク）
- `AdminManagementTest`（既存）に、削除時のトークン失効ケースを追加する

### インフラ

- 変更なし。Phase 15 で追加した Mailpit・`FRONTEND_URL`・`MAIL_*` をそのまま使う。

## 個人情報の取り扱いに関する注記

本フェーズも個人情報（管理者の氏名・メールアドレス）の変更を扱うため、Phase 15 と同じ観点を確認しておく。

| 項目 | 状況 | 備考 |
|------|------|------|
| プライバシーポリシー | 未整備（Phase 15 から変わらず） | 管理者は運営側の人間であり、受講生向けポリシーとは別の整理が要る |
| 同意取得 | 管理者は招待制のため登録フォームなし | 受講生ほどの論点にはならない |
| 削除請求への対応 | 他の管理者による削除で対応（US-4 で残骸の削除も担保） | 管理者にソフトデリートは導入しないため、削除は即時・完全 |
| 収集の最小化 | 氏名・メール・パスワードのみ | 問題なし |
| オプトアウト | 通知メールはリセットのみ（本人操作起点） | 現状は不要 |

## 対象外（Out of Scope）

- 管理者の退会（自己削除）
- 管理者のソフトデリート・復会
- 管理者間の RBAC（権限レベルの分離）
- 管理者の MFA
- 管理者トークンの httpOnly Cookie 化 / Sanctum SPA 認証への移行
- 管理者のメールアドレス変更時の到達確認メール
- 保持期間「30日」等がフロント・メール本文にハードコードされている問題の解消（Phase 15 §15.4 の持ち越し。本フェーズでは触らない）
- プライバシーポリシーページの作成
